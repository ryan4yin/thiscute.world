# Linux 桌面系统系列重写设计

## 目标与读者

把现有七篇「Linux 桌面系统」文章重写成一套以系统学习为主线的系列。目标读者已有一定的 Linux 桌面使用经验，希望理解从开机到关机时各组件的职责、依赖和接口，并能据此独立推导故障的定位方法。排障能力是理解系统之后的结果，不以故障症状组织主体章节。

以作者的 NixOS + systemd +
Wayland 桌面作为连续案例；在机制或实现出现实质差异处，简要对照 Arch
Linux，必要时补充 Fedora、Ubuntu 等发行版。区别 Linux 内核与跨发行版接口、桌面组件的选择、NixOS 的声明式配置，避免将个人配置写成通用默认值。以写作时可核对的官方资料验证这些差异。

## 范围与兼容性

改写 `content/posts/2025/Q3/linux-desktop-explained/index.md` 和
`content/posts/2025/Q4/linux-desktop-{1-boot-security,2-systemd-services,3-session-graphics,4-multimedia-input,5-network,6-shutdown-troubleshooting}/index.md`。保留七篇的目录名、文章 URL、图片资源和现有系列归属；标题、描述、正文、章节顺序及交叉链接可修改。保留现有发布日期，不凭空设置更新日期；按仓库惯例处理实际修订时间。避免不必要地修改主题、部署配置或其他文章。

六篇正文的主要职责如下：

| 篇章               | 主要职责                                                       | 可用的真实案例                                       |
| ------------------ | -------------------------------------------------------------- | ---------------------------------------------------- |
| 零：全景图         | 阅读路径、时间线、关键接口、技术边界                           | 解释案例与证据的阅读方法                             |
| 一：启动与认证     | 固件、引导、内核、根文件系统、PAM 与密钥环                     | 设备名变化导致启动失败；修改登录密码后密钥环不同步   |
| 二：系统服务与通信 | systemd 系统单元、journal、udev、D-Bus 的基础概念              | 从服务状态与日志观察依赖和设备事件                   |
| 三：用户会话与图形 | 登录管理器、用户实例、logind、设备权限、合成器、渲染与应用启动 | 登出后登录管理器自动重启桌面，绕过认证               |
| 四：桌面应用接口   | portal、沙盒、PipeWire、屏幕共享、字体和输入法                 | 自动启动应用与 portal 服务竞态；文档保存或输入法问题 |
| 五：网络           | 网卡、地址、路由、DNS、防火墙、VPN/TUN 与应用的网络路径        | 从挂起恢复后网卡掉链及路由规则变化                   |
| 六：退出与电源状态 | 关机、挂起、恢复、休眠的状态转换与清理                         | 挂起恢复与第五篇网络案例的跨章关联                   |

每个关键机制指定一个主要解释位置。例如 D-Bus 在第二篇解释概念，在后续篇章仅解释相关服务怎样使用它，并链接回第二篇。与桌面主线无关的容器网络、VLAN、多网卡绑定、泛化内核性能调优等内容可删除或转为已有专题链接。避免将第六篇写成重复前五篇的综合故障案例集。

## 每篇的叙述与案例

各篇沿本篇时间线先回答「发生了什么、谁负责、它依赖什么、经由什么接口」，再解释关键边界失效时可以观察什么。章节可按内容调整，不强行套相同标题。只在关系难以用文字说清时使用小图、调用顺序或表格。结尾提供少量只读观察练习：命令、预期能看到的证据、证据不足时不能下的结论。排障步骤以机制推导，而非没有上下文的命令清单。

从 `/home/ryan/nix-config`
的本地实现和 Git 提交历史选择每篇约一至两个真实案例。先核对相关提交及配置差异，再写现象、可证明的证据、机制、改动和验证。提交信息是作者记录的线索，不等于独立复现或完整日志；没有记录的操作、观察与结果不得以第一人称补造。涉及主机细节时仅保留解释机制必需的内容，不引用秘密值或私人标识；不修改该仓库、不进行远程操作。案例可回链对应的仓库提交，但引用前检查目标是否公开且不暴露敏感信息。

## 技术核查与本地验证

对保留或新增的技术结论、发行版差异、命令参数和配置示例逐项核对当前官方资料；无法核实的强断言删去或明确限定条件。优先选择与本机匹配、不会改变状态或泄露敏感信息的命令，在本地逐条运行并检查输出是否支持文章的解释。对适合隔离的操作，只能在受控临时环境验证，记录环境、实际操作和观察结果。本机无法安全执行或不适用的命令明确记录原因，不以「测试通过」代替未执行。

不要为了验证文章而实际触发关机、挂起、休眠、文件系统修复、防火墙清空、网络重配、服务停启或其他可能影响当前机器、可用性、数据、权限和成本的操作。这些示例若不可删去，要标出先决条件、风险、目标确认和恢复方法，并通过官方资料或安全的只读检查验证其解释；不会把危险命令作为默认练习。验证命令不得读取、打印或缓存秘密值。对本机缺少的程序或环境作如实说明。

每篇完成后检查 Markdown 与 Hugo 构建、文章 URL、标题、图片、站内外链接、跨章链接及章节编号，并检查代码块是否把占位符写成可直接执行的命令。记录每篇核查过的来源、实测命令及因安全或环境条件未实测的命令；交付时只报告实际执行过的检查。设计稿不授权部署、推送或任何远程修改。

## 文字风格与审校

使用 `humanizer`
审校正文，并参照作者已有的 NixOS 文章匹配语气。概览篇保留「庖丁解牛」等有作者辨识度的表达；技术正文在适合的位置保留真实的第一人称经历，代码、术语与事实描述保持准确克制。减少密集加粗、装饰性 emoji、列表里的加粗小标题、模板化过渡与空泛总结。性能、安全和发行版选择不作无条件优劣宣称，不凭空添加事实或作者经历。

`humanizer`
用于语言和结构审校，技术示例、元数据、链接及事实是否修改由本设计的核查与兼容性要求决定；审校时再次核对没有引入或删失有依据的主张。

## 实施与验收边界

先建立七篇的机制、案例、来源和命令清单，再分篇改写；每篇检查后统一复核前后衔接、概览导航和实际案例的引用。内容变短不是独立目标：删掉不能为系统学习服务的内容，同时确保保留的机制足以解释案例。

验收标准是读者能沿七篇回答「谁在此阶段行动、为何需要它、它与下一阶段如何相连、在哪里能看到证据」，并能根据一个有记录的故障推导定位方向；文章不会暗示所有发行版或硬件都有同一实现，不会把不安全的操作写成随手可跑的诊断命令。最终不触碰博客以外的运行系统状态或远端。
