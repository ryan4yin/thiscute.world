# Linux 桌面系统系列重写设计

## 目标与读者

从零规划「Linux 桌面系统」系列，以现有七篇文章为素材，重写为一篇概览和八篇主题文章。目标读者已有一定的 Linux 桌面使用经验，希望理解从开机到关机时各组件的职责、依赖和接口，并能据此独立推导故障的定位方法。排障能力是理解系统之后的结果，不以故障症状组织主体章节。

以作者的 NixOS + systemd +
Wayland 桌面作为连续案例；在机制或实现出现实质差异处，简要对照 Arch
Linux，必要时补充 Fedora、Ubuntu 等发行版。区别 Linux 内核与跨发行版接口、桌面组件的选择、NixOS 的声明式配置，避免将个人配置写成通用默认值。以写作时可核对的官方资料验证这些差异。

七个旧文章 URL 分别跳转到新的全景、启动、系统基础、登录会话、音频输入、网络、电源篇；旧「会话与图形」篇跳到登录会话篇，并在该篇明确链接图形篇；旧「启动与安全」篇跳到启动篇，并从中链接登录身份篇。新的图形篇和桌面应用篇无旧 URL。优先使用
[Hugo 官方文档](https://gohugo.io/content-management/urls/#aliases)中的页面 `aliases`
生成旧址的浏览器跳转，再通过本地构建检查生成文件，并核查 Vercel 和 GitHub
Pages 实际采用的托管方式是否满足预期；必要时使用平台支持的规则补充跳转。逐一核对旧址、目标路径、页面内容及没有跳转循环。检查旧章节锚点是否在仓库内被引用：如果引用存在，逐项迁移或为旧锚点提供可到达的入口；不声称普通页面跳转会自动保留改写后的章节锚点。

把概览篇等当前内容里的旧站内链接更新为规范 URL，检查 Markdown、模板、脚本、配置与静态文件中的旧路径。保留
`series: ["Linux 桌面系统"]`，因为年度总结引用了现有系列页。`CHRONICLE.md`
和年度回顾对当年发布「故障排查指南」的叙述属于历史记录，不因新标题而改写；其中如出现实际旧文章链接，仍需保证能到达新版。

`update_statistics.py` 从 GA 的
[`pagePath` 维度](https://developers.google.com/analytics/devguides/reporting/data/v1/api-schema)生成
`data/website_statistics.json`，排行模板以 `pagePath`
作为链接。GA 中的旧路径历史数据不修改、不归并到新稿，也不按拆篇比例虚构分配：新页面各自从新路径累计。明确区分该脚本既有的其他文章路径合并规则与本系列的新旧稿统计口径。如果旧版路径进入阅读排行，显示「旧版文章」并让入口跳到对应的新篇；新稿只显示真实新路径数据。不得凭空改写已生成的 GA 统计值；通过不依赖 GA 凭据的本地样例数据验证新旧路径分离、标题标识、排行链接和合并逻辑。既有全站统计仍依据 GA 原始数据，设计不授权调用线上 GA 的写接口。

## 每篇的叙述与案例

各篇沿本篇时间线先回答「发生了什么、谁负责、它依赖什么、经由什么接口」，再解释关键边界失效时可以观察什么。章节可按内容调整，不强行套相同标题。只在关系难以用文字说清时使用小图、调用顺序或表格。结尾提供少量只读观察练习：命令、预期能看到的证据、证据不足时不能下的结论。排障步骤以机制推导，而非没有上下文的命令清单。

从 `/home/ryan/nix-config`
的本地实现和 Git 提交历史选择每篇约一至两个真实案例。先核对相关提交及配置差异，再写现象、可证明的证据、机制、改动和验证。提交信息是作者记录的线索，不等于独立复现或完整日志；没有记录的操作、观察与结果不得以第一人称补造。涉及主机细节时仅保留解释机制必需的内容，不引用秘密值或私人标识；不修改该仓库、不进行远程操作。案例可回链对应的仓库提交，但引用前检查目标是否公开且不暴露敏感信息。

## 技术核查与本地验证

先对计划写入的技术知识点、发行版差异、命令、配置和机制解释逐项进行在线资料搜索；优先采用官方手册、项目文档、规范及项目维护者的一手资料，并将参考链接写在对应篇章的相关段落。NixOS 与 Arch
Linux 对照先查各自当前官方文档和适用的上游文档；博客文章、论坛和 AI 回答只能作为发现问题的线索，不能单独支持技术结论。与作者亲历有关的事实只从仓库配置、提交及明确的作者记录提取，不因为网上出现相似案例就推断作者经历相同。完成资料核对后，对每条命令判断环境适用性及副作用；优先选择与本机匹配、不会改变状态或泄露敏感信息的命令，在本地逐条运行并检查输出是否支持文章的解释。对适合隔离的操作，只能在受控临时环境验证，记录环境、实际操作和观察结果。本机无法安全执行或不适用的命令明确记录原因，不以「测试通过」代替未执行。不能由资料或观察支撑的强断言删去或明确限定条件。

不要为了验证文章而实际触发关机、挂起、休眠、文件系统修复、防火墙清空、网络重配、服务停启或其他可能影响当前机器、可用性、数据、权限和成本的操作。这些示例若不可删去，要标出先决条件、风险、目标确认和恢复方法，并通过官方资料或安全的只读检查验证其解释；不会把危险命令作为默认练习。验证命令不得读取、打印或缓存秘密值。对本机缺少的程序或环境作如实说明。

每篇完成后检查 Markdown 与 Hugo 构建、文章 URL、标题、图片、站内外链接、跨章链接及章节编号，并检查代码块是否把占位符写成可直接执行的命令。保留逐篇的「知识点与官方来源、案例与提交证据、命令与本地结果、未实测原因」核查记录；交付时只报告实际执行过的检查。设计稿不授权部署、推送或任何远程修改。

## 文字风格与审校

使用 `humanizer`
审校正文，并参照作者已有的 NixOS 文章匹配语气。概览篇保留「庖丁解牛」等有作者辨识度的表达；技术正文在适合的位置保留真实的第一人称经历，代码、术语与事实描述保持准确克制。减少密集加粗、装饰性 emoji、列表里的加粗小标题、模板化过渡与空泛总结。性能、安全和发行版选择不作无条件优劣宣称，不凭空添加事实或作者经历。

`humanizer`
用于语言和结构审校，技术示例、元数据、链接及事实是否修改由本设计的核查与兼容性要求决定；审校时再次核对没有引入或删失有依据的主张。

## 实施与验收边界

先建立九篇的机制、案例、来源和命令清单，再分篇改写；每篇检查后统一复核前后衔接、概览导航、旧址映射、统计展示和实际案例的引用。内容变短不是独立目标：删掉不能为系统学习服务的内容，同时确保保留的机制足以解释案例。

验收标准是读者能沿九篇回答「谁在此阶段行动、为何需要它、它与下一阶段如何相连、在哪里能看到证据」，并能根据一个有记录的故障推导定位方向；文章不会暗示所有发行版或硬件都有同一实现，不会把不安全的操作写成随手可跑的诊断命令。七个旧址可到达对应新稿，站内新链接正确，GA 旧版和新版的页面指标不互相归并。最终不触碰博客以外的运行系统状态或远端。
